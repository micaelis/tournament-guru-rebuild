# Deploying Tournament Guru to a client-owned Supabase project

This is the step-by-step handoff checklist for bootstrapping a fresh, client-owned Supabase project from this repo. Run each section in order. Steps marked ⚠ change external state — read the whole section before running.

The reference staging project (`nmdwccyzaofqoginsyja`) already has these migrations applied; use it to sanity-check any step against a working example.

---

## 0. Prerequisites

- Supabase CLI **v2.98.0+** (`supabase --version`).
- `psql` (any recent version).
- `curl` and `jq` for the verification curls.
- The client already has a Supabase organization; you have access to create a new project inside it.

---

## 1. Create the fresh Supabase project ⚠

Dashboard → your org → **New project**.

- **Region**: match the client's user population (US-East for US-based youth-sports orgs).
- **Postgres version**: **17.x** (this schema targets PG 17 idioms — `search_path` includes `pg_temp` on every SECURITY DEFINER function, views pin `security_invoker=false` explicitly).
- **Database password**: use a password manager. This is the `postgres` superuser password; you'll need it for the `psql -f schema.sql` step.

Wait for the project to come up (usually 30–60 s). Then, from **Project Settings → API**, note down:

- `Project URL` (looks like `https://<ref>.supabase.co`)
- `Project API keys → anon public`
- `Project Reference ID` (the `<ref>`)

You'll wire these into the app's env vars in step 5.

---

## 2. Bootstrap the schema ⚠

The consolidated schema is at [`supabase/schema.sql`](supabase/schema.sql). It's auto-generated by [`scripts/build-schema.sh`](scripts/build-schema.sh) from every migration in [`supabase/migrations/`](supabase/migrations/), **minus** the two demo seeds. Running it once against a fresh DB produces the app's full final schema state (tables, RLS + policies, triggers, RPCs with pinned `search_path`, grants, indexes, and the small lookup seeds).

```bash
# Get the connection URL from Project Settings → Database → Connection string
# (use the "Direct connection" URI, NOT the pooled one — DDL needs a real session).
export DATABASE_URL="postgres://postgres:<db-password>@<ref>.db.supabase.co:5432/postgres"

# Regenerate schema.sql from the migrations tree (belt-and-braces — nothing
# should have drifted, but this catches it if it has).
bash scripts/build-schema.sh

# Apply.
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/schema.sql
```

Watch for `ON_ERROR_STOP` aborts. The schema is idempotent for the parts that need to be (`create table if not exists`, `create or replace function/view`) and deliberately non-idempotent where a re-run would be a bug (`create trigger`, `enable row level security` — Postgres errors if RLS is already on, which tells you the schema was already applied).

### 2b. Alternative: apply via the CLI's migration tree

If you'd rather keep the timestamped migration history in `supabase_migrations.schema_migrations`, link the CLI and push instead of running `schema.sql`:

```bash
supabase login
supabase link --project-ref <ref>
supabase migration list --linked   # should show 34 pending
supabase db push                   # applies migrations in order
```

Either path lands the same final state. `schema.sql` is faster for a client cold-start; `db push` is friendlier if the client's team will iterate on migrations afterward.

## 3. Storage buckets + policies ⚠

The app references stored files at seven places (see [`supabase/proposals/h3_storage_bucket_policies.sql`](supabase/proposals/h3_storage_bucket_policies.sql)). Create three buckets with the exact names the app expects:

| Bucket name       | Public? | Used for                                              |
|-------------------|---------|-------------------------------------------------------|
| `public-avatars`  | yes     | `profiles.profile_picture`, `profiles.org_logo`       |
| `public-events`   | yes     | `events.logo`, `events.photos[]`, `sponsors.logo`, `testimonials.photo` |
| `private-csv`     | no      | `submitted_csvs.file_path`                            |

**Dashboard → Storage → New bucket** for each. Set `public` to the value in the table.

Then apply the policies:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/proposals/h3_storage_bucket_policies.sql
```

The proposal file assumes:
- Object paths use `<owner_uuid>/…` for avatars and `<event_uuid>/…` for event assets.
- `testimonials/…` prefix is admin-write only, in the `public-events` bucket.
- CSV uploads are keyed by `<user_uuid>/…` in the private bucket.

If the client's upload flow uses different path conventions, adjust `storage.foldername(name)[1]` accordingly.

## 4. Auth configuration ⚠

Dashboard → **Authentication → URL Configuration**:

- **Site URL**: the client's production domain (e.g. `https://tournamentguru.com`).
- **Redirect URLs**: add each of
  - `https://<production-domain>/auth/callback`
  - `https://<staging-or-preview-domain>/auth/callback` (optional)
  - `http://localhost:3000/auth/callback` (for local dev; drop if the client doesn't want it)

Dashboard → **Authentication → Providers → Email**:

- ✅ **Enable email signups**
- ✅ **Enable email confirmations** — this is REQUIRED in production. `supabase/config.toml` sets it OFF for local dev only, and the app's anti-enumeration behavior in [`app/(auth)/actions.ts`](app/(auth)/actions.ts) relies on Supabase suppressing confirmation emails for already-registered addresses.
- Confirmation email template: customize with the client's branding.
- **Confirm email change**: on.
- **Secure email change**: on.
- Minimum password length: 12 (matches the app's own `validatePassword`).

Dashboard → **Authentication → SMTP**:

- ⚠ Never ship prod using Supabase's default email service — its outbound cap is ~4 emails/hour and unrated for prod. Wire the client's SMTP:
  - Postmark, Resend, SendGrid, or the client's own SMTP host.
  - Sender: `no-reply@<client-domain>` (or whatever the client's DKIM'd domain is).
  - Sender name: match the app title.

Dashboard → **Authentication → Rate Limits**:

- Sign-in / sign-up / reset all default to reasonable Supabase values. Only lower them if the client has an unusual abuse profile.

Verify SMTP by triggering a real reset from the production `/reset` route with a mailbox you control, then confirming the email arrives.

## 5. App env vars ⚠

On Vercel (or wherever the app is hosted), set:

```
NEXT_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon key from Project Settings → API>
NEXT_PUBLIC_SITE_URL=https://<production-domain>
```

- Scope: `Production`, `Preview`, and `Development` if you want previews to hit the same DB.
- **Never** commit these to the repo. `.env.local` is gitignored.
- **Never** put the `service_role` key anywhere the browser can see it. This app doesn't use `service_role` from the app runtime; if a future feature does, it goes in a *server-only* env var (no `NEXT_PUBLIC_` prefix).

Redeploy so the new env vars take effect.

## 6. Post-deploy verification

Run each check against production. Every one MUST pass before handing the project off.

Load helper vars:

```bash
export SB_URL="https://<ref>.supabase.co"
export SB_ANON="<anon key>"
```

### 6a. RLS lockdowns are live

```bash
# C1 — profile update policy has a WITH CHECK expression
psql "$DATABASE_URL" -c "select policyname, cmd, with_check from pg_policies where tablename='profiles' and policyname='profiles: self update';"
# expect: with_check contains 'user_type IN'

# C1/R2 — reviews insert policy has a WITH CHECK on moderation fields
psql "$DATABASE_URL" -c "select policyname, cmd, with_check from pg_policies where tablename='reviews' and policyname='reviews: author insert';"
# expect: with_check contains 'published' AND 'guru_review' AND 'flagged'

# C2 — RLS on cards + promo_codes
psql "$DATABASE_URL" -c "select relname, relrowsecurity from pg_class where relname in ('cards','promo_codes');"
# expect: both relrowsecurity = t

# H2 — RLS on event child tables + sponsors + event_profiles + testimonials + submitted_csvs + recently_viewed + profile_age_prefs
psql "$DATABASE_URL" -c "select relname, relrowsecurity from pg_class where relname in ('event_ages','event_genders','event_fields','event_features','event_competition_levels','event_age_groups','sponsors','event_profiles','testimonials','submitted_csvs','recently_viewed','profile_age_prefs') order by relname;"
# expect: every relrowsecurity = t
```

### 6b. C3 — anon can't read reviewer email

```bash
curl -sS "${SB_URL}/rest/v1/reviews?select=user_email&limit=1" \
  -H "apikey: ${SB_ANON}" \
  -H "Authorization: Bearer ${SB_ANON}"
# expect: 403 or an error mentioning 'permission denied for column user_email'.
# If it returns rows with user_email present → C3 didn't apply; STOP.

curl -sS "${SB_URL}/rest/v1/reviews?select=id,review_title,overall_rating&limit=1" \
  -H "apikey: ${SB_ANON}" \
  -H "Authorization: Bearer ${SB_ANON}"
# expect: 200 with a JSON array (the app's actual anon SELECT still works).
```

### 6c. C5 — get_event_directors doesn't leak email

```bash
curl -sS "${SB_URL}/rest/v1/rpc/get_event_directors" \
  -H "apikey: ${SB_ANON}" \
  -H "Authorization: Bearer ${SB_ANON}" \
  -H "Content-Type: application/json" \
  -d '{"p_limit":5,"p_offset":0}' | jq '.[0] | keys'
# expect: an array of column names that does NOT include "contact_email".
```

### 6d. R1 — rate_limit_touch is not anon-callable

```bash
curl -sS "${SB_URL}/rest/v1/rpc/rate_limit_touch" \
  -H "apikey: ${SB_ANON}" \
  -H "Authorization: Bearer ${SB_ANON}" \
  -H "Content-Type: application/json" \
  -d '{"p_bucket":"search_queries","p_limit":999999999}'
# expect: 401 or 404 or an error mentioning 'permission denied'.
# If it returns null / {} / 204 → R1 didn't apply; STOP.
```

### 6e. R2 — can't self-publish or self-award Guru

Requires a real signed-in JWT (create a test user first). Then:

```bash
# Replace TEST_JWT with a real Authorization: Bearer <access_token> from a
# signup + email-confirm flow through the app.
curl -sS "${SB_URL}/rest/v1/reviews" \
  -H "apikey: ${SB_ANON}" \
  -H "Authorization: Bearer ${TEST_JWT}" \
  -H "Content-Type: application/json" \
  -d '{"author_id":"<test-user-uuid>","event_id":"<any-event-uuid>","review_title":"probe","review_body":"probe","overall_rating":5,"published":true,"guru_review":true}'
# expect: 400 or 42501 permission denied for column published (or a policy violation on with_check).
```

### 6f. Storage buckets exist and are policy'd

```bash
supabase storage ls --linked
# expect: three lines: public-avatars, public-events, private-csv.

psql "$DATABASE_URL" -c "select policyname from pg_policies where schemaname='storage' and tablename='objects' order by policyname;"
# expect: entries for each of the three buckets' read/write/delete policies.
```

### 6g. Auth headers are on the app

```bash
curl -sI "https://<production-domain>/" | grep -E 'strict-transport-security|x-frame-options|x-content-type-options|referrer-policy|permissions-policy|cross-origin-opener-policy'
# expect: six headers, values per next.config.ts.
```

If any check fails, stop and fix. Handing off with a failed check is worse than not handing off.

## 7. Seed data (optional)

For a demo dataset without shipping real users' PII:

```bash
# Point at the SOURCE (usually staging) to derive the seed from.
DATABASE_URL='postgres://…staging…' bash scripts/generate-seed-dummy.sh
# → writes supabase/seed.dummy.sql

# Load into the FRESH prod (or a client-side demo project).
psql "$TARGET_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/seed.dummy.sql
```

The script scrubs every email to `user_<uuid8>@example.test`, empties `cards` / `promo_codes` / `contact_requests` / `submitted_csvs` / `transactions`, and nulls `profiles.stripe_id`. It ends with two verification `SELECT`s that MUST return zero rows — if either does return rows, the seed file leaked a real email and MUST NOT be shipped.

Do **not** run the two demo-only migrations (`20240101000010_refresh_event_dates_for_demo.sql`, `20240101000015_seed_bubble_recent_reviews.sql`) against a populated database. They're excluded from `schema.sql` for this reason and carry DO-NOT-RE-RUN banners.

## 8. Handoff artefacts

Give the client:

1. This `DEPLOYMENT.md`.
2. `AUDIT.md` — the original security audit.
3. `CHANGES.md` — the changelog from the refactor.
4. The [staging project URL](https://supabase.com/dashboard/project/nmdwccyzaofqoginsyja) as a "working reference" they can compare their fresh project against.
5. Their own `.env.production` template with the three env-var names filled in but the values redacted.

Handoff is complete when: they can boot the app locally against their fresh Supabase project, sign up, complete onboarding, and browse events. Then delete your `SUPABASE_ACCESS_TOKEN` and any local `.env.local` pointing at their project.
